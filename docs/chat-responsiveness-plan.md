# 长会话 UI 响应性改进计划

日期：2026-09-10

状态：核心优化已实现并通过定向测试、完整测试集及生产构建 Electron 核心场景对照。19/23 项已完成；开发构建、多窗口和完整交互验收仍待补，全量类型检查受既有输入框错误阻挡。

## 1. 目标与范围

用户现象：消息内容较多时，发送新消息或删除指定的一整条会话，会让整个 UI 暂时无响应，等待一会儿后恢复。

本计划要解决的是交互线程被长任务占用，而不只是让请求更快返回。必须分别记录“下一帧能否响应”和“删除、加载是否完成”，不能用缩短网络等待或增加 loading 遮罩替代响应性优化。

纳入范围：

- 整会话删除后的事件广播、缓存失效、历史读取与工具状态重建。
- 删除当前会话后的替代会话选择、加载和渲染。
- 发送新消息、逐条提交消息及运行收尾的历史更新。
- 输入草稿与消息列表之间的渲染隔离。
- 历史执行过程的折叠状态、挂载成本及必要时的窗口化。

已获授权实施本计划；全部性能探针使用隔离数据，不操作真实会话、数据库或附件。实施不得顺带更改删除语义、运行中保护、工具协议或现有国际化约定。

## 2. 已有证据与边界

本节保留优化前的调查记录，不能再作为当前实现的描述；实施后的测量见第 8 节。

| 观察 | 已验证的行为 | 证据边界 |
| --- | --- | --- |
| 删除一整条会话 | 删除后广播 `sessions:changed`，应用会重新读取所有已创建且空闲的会话状态，包括其他工作区 | 已检查实际调用链，并用实际刷新函数和模拟 IPC 复现 |
| 工具状态重建 | 每条含工具的消息都复制累计工具对象，消息增加时成本近似平方级增长 | V8 合成测量：2000 次工具调用约 0.38 秒，5000 次约 3 秒；不是纯文本消息数量 |
| 删除小会话影响其他历史 | 两条未变化的长会话，各含 2000 次工具调用，删除后的刷新仍处理它们 | Node/V8 + 模拟 IPC 的事件循环延迟约 834ms；不含真实 IPC、数据库和 React 渲染 |
| 整会话删除 SQL | 无附件的 2000 条纯文本会话删除约 7ms，10000 条约 38ms | 每条约 1.1KB，仅纯内存 SQLite；不能排除真实磁盘、附件和子会话带来的额外成本 |
| 运行收尾与历史替换 | `replaceHistory` 逐条写消息，每条又更新全会话 FTS 标题，即使标题未变 | 保留 598 条消息触发 599 次标题更新，累计更新约 18 万行次，占一次测量耗时约 89% |
| 发送后的折叠切换 | 只有末轮整体折叠；追加消息后，上一轮的中间内容可能重新挂载 | Bun/JSDOM 合成测量：250 个中间步骤从 1 块 Markdown 增至 251 块，约 0.26-0.31 秒；不含浏览器布局、绘制 |
| 状态订阅与历史渲染 | `ChatView` 订阅整个会话状态，`Thread` 遍历完整历史；正文 Markdown 已有 `memo` | 已确认结构，尚未在真实窗口单独测量草稿输入的成本 |

必须保留的区分：

- **删除整条会话不走 `replaceHistory`。** 不得把“删一轮问答”的秒级历史重写耗时直接归因到整会话删除。
- 主进程阻塞与渲染线程阻塞要分别采样；主进程忙不能单独证明所有前端交互都被冻结。
- Bun 使用 JavaScriptCore，Electron 使用 V8；两者实测差异明显，不能混用绝对耗时。
- 内存数据库没有磁盘等待，JSDOM 没有真实布局、绘制。上述数据只用于定位风险和建立对照，不能视为生产基线。
- 现有 [消息列表设计文档](./message-list-design.md) 是设计参考，不代表当前实现已经具备虚拟化、分页和旁路流式渲染。

## 4. 分阶段方案

### 阶段 A：固定真实基线

优先复用现有 Vitest 和 Electron/CDP 探针模式，不先建设新的性能平台。

1. 建立合成数据集，覆盖纯文本、长 Markdown、工具调用、子代理、附件和多个已加载会话。
2. 使用独立数据库与附件目录。当前数据库默认位置依赖工作目录，仅修改 Electron `user-data-dir` 不足以保证数据隔离。使用本地模拟上游，避免真实模型请求和费用。
3. 在同一台机器记录 Electron、V8、构建模式、消息数、正文大小、工具数、已加载会话数和附件数。开发构建与生产构建分开记录。
4. 记录操作到下一次绘制、IPC 往返、SQL、附件清理、每个会话的读取次数、状态重建、React 提交、Markdown 挂载数和长任务。必要时记录 GC 与堆大小。
5. 性能记录仅保留 ID、数量、耗时及必要的合成样本，不采集用户正文、凭证或真实附件内容。

核心场景见第 5 节。后续每一阶段只重跑与改动相关的场景，阶段收尾再做组合回归。

### 阶段 B：收窄删除和消息提交后的刷新

优先级最高，直接对应整会话删除场景。

1. 为会话事件明确区分列表元数据变化、消息提交、历史替换、会话删除与批量导入/恢复/清理。负载携带受影响的会话 ID；工作区 ID 仅辅助定位，不能代替会话级范围。
2. 删除事件携带实际删除集合，包括派生子会话。数据库已有子树删除逻辑，应复用其结果，不在 UI 另写一套推断。
3. 列表元数据变化只更新列表和标题；删除只清理对应缓存与 Tab；历史替换只刷新受影响的已加载会话。消息提交沿用现有 Agent 增量事件，不因此重读无关空闲会话。
4. 全量刷新仅保留给真正的全量数据操作。兼容旧事件形状时明确回退策略，并覆盖全部生产者和消费者，不能直接忽略通知而留下陈旧历史。
5. 合并同会话重复读取，防止旧请求覆盖新状态；删除后的迟到回包不得恢复已删除缓存。保留已有运行中会话和后台子代理保护。
6. 明确由一个入口负责选择替代会话，避免事件消费者和删除回调重复开关 Tab。保留当前“优先下一条，否则上一条，无剩余时进入新对话”的行为。

验收要点：删除未激活的小会话时，无关会话的 `sessions:get`、工具重建及 transcript 替换次数均为 0；同工作区与跨工作区都要成立。

### 阶段 C：线性重建历史工具状态

1. 将历史重建与不可变事件归约区分开。在重建函数内部创建新的局部容器，一次扫描消息和内容块，最后按现有规则合并 live 信息。
2. 不得直接把共用的 `applyToolMessage` 改为原地修改；它还承担事件归约职责，旧状态快照和调用方输入必须保持不可变。
3. 保留工具结果、错误状态、授权后参数、开始/结束时间及流式较新状态的优先级。被删除的工具不能因合并旧缓存而重新出现。
4. 单独测量子代理重建；如果发现相同的累计复制问题，再在该重建边界处理，不顺带重写子代理协议。
5. 以消息、内容块和工具总量的线性增长为目标。单元测试验证结果与引用不变性，性能对照验证增长趋势，避免在普通 CI 测试中使用脆弱的固定毫秒断言。

验收要点：5000 次工具调用不再产生秒级同步重建；样本规模增大时不能继续呈现近似平方级增长。

### 阶段 D：减少发送与运行收尾的持久化工作

此阶段是独立瓶颈，不能作为阶段 B 的替代。

1. 只有规范化后的标题真正变化时才同步 FTS 标题；正常更新时间、消息提交不得重写全部历史的搜索标题。
2. 在批量历史处理期间合并会话元数据更新，避免每写一条消息就重复执行会话级工作。
3. 保留 `replaceHistory` 的权威替换语义，但让未变化的内容走短路或增量对账；需要调整顺序时继续保证消息顺序唯一约束。
4. 检查运行 `finally` 中的全量对账。不得直接删除收敛逻辑：必须先验证正常结束、停止、异常和后台子代理较新回执都能可靠落库。
5. 保留消息与工具结果配对、`run_id` 和历史用量归属、附件引用及事务回滚。标题重命名和导入后的全文检索仍必须正确。

验收要点：标题不变的普通消息提交产生 0 次全会话 FTS 标题更新；未变化的历史对账不再逐条重写全部正文和索引。

### 阶段 E：稳定历史渲染与折叠状态

1. 历史回合是否折叠不再仅取决于“是否为最后一轮”。保留稳定的组件身份和用户展开意图，追加消息不得使上一轮的中间 Markdown 批量重新挂载。
2. 历史回合的已完成状态不能复用当前 run 的状态。错误、后台子代理活动和用户主动展开的内容必须保持可发现、可访问。
3. 隔离 Composer 草稿和历史列表的订阅。只有草稿、队列或附件托盘变化时，不应重新处理未变化的历史。
4. 为历史回合提供稳定的数据和回调边界，再按实际渲染证据增加缓存。保留已有 Markdown 缓存，不以堆叠 `memo` 代替控制更新范围。
5. 验证流式转提交、编辑、重新生成、删除末轮、复制、用户展开状态及自动滚动，避免性能优化带来身份变化或滚动跳动。

验收要点：追加一条短消息后，上一轮未变化内容的 Markdown 新挂载数为 0；仅修改草稿不触发历史行正文重新渲染。

### 阶段 F：按剩余瓶颈决定结构性优化

完成前述局部优化并复测后，再作决定，不预先引入新依赖。

- 如果冷启动长历史或大量 DOM 仍产生长任务，评估历史分页、窗口化和虚拟列表。验证动态高度、向上加载锚点、贴底跟随、图片/图表完成加载、查找与复制、键盘操作和可访问性。
- 如果实际数据库或附件清理仍长时间阻塞主进程，先收窄附件查询与扫描，再评估异步文件操作或数据库移入专用进程。必须保留共享附件引用校验、托管路径边界、符号链接处理和失败报告。
- 若批准数据库进程隔离，单独设计事务顺序、取消、退出收尾和故障恢复，不能仅用 `Promise` 包装同步 SQLite 调用。
- 每项评估必须记录“需要实施”或“暂不实施”及证据。选择暂不实施不等于已完成对应优化。

## 5. 验收场景与标准

| 场景 | 数据与操作 | 必须验证 |
| --- | --- | --- |
| 删除非当前小会话 | 同时加载两条长工具历史，其中一条在另一工作区 | 无关历史不读取、不重建、不替换；输入和点击继续响应 |
| 删除当前会话 | 替代项分别为已加载长会话、未加载长会话、无剩余项 | 替代选择正确，所有指向被删会话的 Tab 清理，无重复新对话；区分响应时间与加载完成时间 |
| 会话级联与附件 | 父/子会话、草稿附件、共享附件、无法删除文件、非托管路径 | 删除集合正确，不误删共享或外部文件；数据库失败不提前丢失 UI 状态；物理清理失败如实报告 |
| 事件并发 | 快速重复通知、历史请求未返回时删除、旧回包晚于新回包 | 无重复全量读取，无状态倒退或缓存复活，运行中保护不变 |
| 发送与收尾 | 长历史继续发送，正常完成、停止、异常、后台子代理更新 | 无关会话不刷新，收尾无全量索引重复写入，持久化语义正确 |
| 渲染交互 | 输入草稿、追加消息、展开历史、向上滚动、图片和图表加载 | 历史不无故重挂，展开意图保留，无强制跳底和明显布局抖动 |

建议性能门槛，待阶段 A 的真实基线确认后固定：

- 核心场景的操作到可见反馈 p95 不高于 100ms；异步数据加载完成时间单独统计。
- 不出现应用“无响应”，重点操作不应引入超过 50ms 的连续渲染主线程任务。超标必须记录归因，不能用平均值掩盖。
- 在固定 V8 环境中，5000 次工具调用的重建以低于 50ms 为初始目标；若仍超标，继续处理剩余计算或拆分任务，不能只改善增长趋势就关闭问题。
- 对需要真实测量的交互至少进行 20 次操作，分别记录首次加载、稳定重复操作的 p50、p95、最大长任务和样本规模。
- 时间门槛用于固定环境的性能验收；CI 优先约束无关读取次数、索引更新次数、状态正确性与渲染挂载次数。

测试与检查：

```sh
bun run typecheck
bunx vitest run src/renderer/src/stores/__tests__/tool-history.test.ts src/renderer/src/stores/__tests__/turn-delete.test.ts src/main/db/__tests__/turn-usage.test.ts
```

以上只是已知相邻用例，不是完整验收范围。实施时将新增的定向用例加入对应命令，对实际改动的 TypeScript 文件执行 ESLint；共享转录或持久化变更整合后执行 `bun run test`。真实 Electron 场景单独运行，不以单元测试通过代替响应性验收。既有失败单独记录，不顺带修复无关问题。

如新增用户可见状态、错误或提示，必须通过 renderer i18n，覆盖 `zh-CN` 与 `en-US`，不得直接写入 JSX/TSX。

## 8. 实施结果与剩余验收

### 可复核的测量

环境：同一台 macOS，应用 0.1.12、Electron 44.1.1、Chrome 152.0.7977.65、Electron 内 Node 24.19.0。使用 `electron-vite build` 产物启动的未打包窗口，不是签名安装包，也不是开发热更新模式。每个表中场景均为 20 次样本；原始结果保留在 `os.tmpdir()` 下的独立目录中。

`feedbackMs` 在删除场景表示确认点击到首次 RAF 回调；发送场景表示用户消息已进入 DOM 后的首次 RAF。后续删除探针另有 `visibleFeedbackMs`，确认菜单与侧边栏目标均消失。RAF 表示进入下一帧的机会，不等同于显示器的实际呈现时间。`completeMs` 包含一次后续 RAF，并等待目标删除或回复完成；长任务取 PerformanceObserver 的 renderer `longtask`，不直接等同于主进程 SQL 耗时。

| 场景 | 数据与构建阶段 | 反馈 p95 | 完成 p95 | 最大 renderer 长任务 |
| --- | --- | --- | --- | --- |
| 删除非当前小会话，优化前 | 两条已缓存历史，各 1000 次工具调用 | 119.7ms，首帧 | 139.4ms | 58ms |
| 删除非当前小会话，最终版本 | 同规模 | 19.8ms，首帧及可见删除 | 39.7ms | 无 |

| 发送，渲染隔离后 | 同规模；本机模拟上游即时回复 | 19.9ms，可见用户消息 | 80.2ms | 无 |

| 删除当前会话，未加载替代项 | 每次全新替代历史含 2000 次工具调用 | 27.9ms，可见删除 | 39.8ms，含历史加载 | 无 |

### 结构性优化决定

- F01：在已测的折叠工具历史和 2000 次工具调用冷加载规模下暂不引入虚拟化。数百轮纯正文、大量手动展开的中间过程及多媒体同时布局尚未纳入本次性能对照；不能据此承诺任意历史长度都无长任务。若这些场景确认超标，再追加分页/虚拟化实现与滚动锚点验收任务。
- F02：本机 SSD、每会话 100 个小文件的删除未显示超标等待，暂不改为异步清理或独立数据库进程。仍保留同步引用扫描和文件操作；巨大附件引用表、网络盘、低速磁盘及超大文件批次需要另测。没有以 Promise 包装同步 SQLite 来冒充隔离。

## 9. 运行取消与挂起修复

2026-09-10 用户追加反馈：部分任务长时间显示运行中，点击停止也无法结束。以下修复不表示 A02、E03、G01、G02 已全部验收。
